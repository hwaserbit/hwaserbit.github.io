## 4. 데이터 관리 및 운영 전략 (Operations & Backup)

시스템이 파편화됨에 따라 형상 관리와 데이터 백업 전략을 명확히 정의했습니다.

1. **GitOps 기반 인프라 관리**: 
   모든 노드의 Docker Compose, YAML 설정 파일, 쉘 스크립트는 중앙 Git 리포지토리에 스냅샷 형태로 기록됩니다. 이를 통해 특정 노드에 장애가 발생하더라도 코드 기반으로 동일한 환경을 즉시 배포(Redeploy)할 수 있습니다.
2. **NFSv4 및 SMB 프로토콜 분리**:
   서버 간의 통신(컨테이너의 데이터 볼륨 마운트 등)은 오버헤드가 적고 권한 관리가 명확한 **NFSv4**(`vers=4.1, rsize=1M, wsize=1M` 옵션 적용)를 표준으로 사용하며, 사용자 PC(Windows/Mac)에서의 파일 접근은 **SMB** 프로토콜로 분리하여 네트워크 병목을 방지했습니다.
3. **분산 백업 및 동기화**:
   작지만 치명적인 서비스 설정 파일들은 **Syncthing**을 통해 H4-Plus, 13600K, 8505 Ubuntu VM 간에 3중 복제 및 동기화를 수행합니다. 대용량 미디어 파일은 단일 백업의 한계가 존재하므로, 향후 HDD를 추가하여 증분 백업 아키텍처를 별도로 설계할 계획입니다.

## 5. 능동형 전력 제어 (HEMS 연동)

개인 홈랩의 가장 큰 적은 누진세입니다. 이를 억제하기 위해 Home Assistant(HAOS)와 연동한 동적 전원 관리 시스템을 구현했습니다.

- **절전 파이프라인**: 스마트폰의 삼성 헬스(Samsung Health) 수면 데이터를 API로 트래킹하여, 관리자가 수면 상태에 진입하면 모든 연산 노드(13600K 등)에 Graceful Shutdown 명령을 전송합니다. API 장애를 대비해 새벽 3시 하드 리미트 종료 룰셋도 이중화해 두었습니다.
- **자동 기상 (WOL)**: 아침 기상 시점에 맞춰 HAOS가 Wake-On-LAN 매직 패킷을 브로드캐스팅하여 노드를 기동시킵니다. 향후 구축 예정인 DIY 태양광 ESS(에너지 저장 장치)의 발전량 데이터와 연동하여, 잉여 전력이 일정 수준을 초과할 때만 AI 연산 서버를 가동하도록 알고리즘을 고도화할 계획입니다.


### 1. 하드웨어 도입 및 퇴역(교체) 히스토리

**① 메인 스토리지 서버 교체 (HP Z640 → ODROID-H4 PLUS)**

- **Z640 퇴역 사유**: Xeon E5-2690 v4와 128GB ECC RAM을 갖춘 훌륭한 장비이나, 아이들(Idle) 상태에서도 평균 65W 이상의 전력을 소모하여 24시간 무중단 개인 서버로 유지하기에는 누진세 부담이 큼.
    
- **ODROID-H4 PLUS (N97) 도입 배경**: N100(TDP 6W) 대비 TDP는 12W로 다소 높지만, 베이스 클럭(1.2GHz)과 부스트 클럭(1.6GHz)이 더 높아 체감 성능이 우수함. 또한 국내 하드웨어 제조사(하드커널)의 생태계를 응원하고 산업에 기여하고자 하는 개인적인 의미도 포함되어 도입을 결정함.
    

**② AI/컴퓨팅 서버 교체 (i7-6700 → i5-13600K)**

- **교체 사유**: 친구에게 받은 i7-6700 시스템에 Intel Arc A770 16GB를 장착하여 사용하려 했으나, 6세대 구형 플랫폼은 GPU의 VRAM을 100% 활용하기 위한 필수 기술인 **ReBAR(Resizable BAR)**를 지원하지 않음. 이로 인해 GPU 성능을 10~20%밖에 끌어내지 못하는 병목이 발생하여, 이를 완벽히 지원하는 최신 플랫폼(13600K)으로 인프라를 전면 교체함.
    

**③ 백업 라우터 구축 실패 (M600 보류)**

- **원래 계획**: IPTV 무중단 환경(페일오버)을 유지하기 위해 Pentium J3710 기반의 Lenovo M600 미니 PC(SSD 120GB 활용)에 네이티브 pfSense를 설치하여 백업 라우터로 운용할 예정이었음.
    
- **실패 사유**: 장비의 물리적 랜 포트 고장이 발견되어 당장 실현이 불가능해짐. 추가 장비 구매는 RAM 가격 상승 등 예산 문제로 보류하고 장비는 창고에 보관 중.
    

**④ 통신사 공유기 (KT 공유기) 삽질**

- **이슈**: KT 공유기의 기본 대역(`172.30.1.0/24`)이 고정되어 있어 보안 제한을 우회하거나 뚫어보려 시도했으나 실패함. 결국 통신사 장비의 한계를 인정하고 단순 경험(삽질)으로 남겨둠.

### 2. 파일 시스템 및 스토리지 구성에 대한 고민

**① ZFS 도입 보류와 ext4 유지**

- **초기 계획**: H4-Plus에 ZFS를 도입하여 스냅샷 기반의 2차 저장소 복제(Send/Receive)를 구현하려 함.
    
- **보류 사유**: ZFS를 구성하려면 디스크 포맷이 필수적인데, 현재 보관 중인 영상/사진/문서 데이터의 용량이 너무 방대하여 백업 후 포맷하는 과정이 현실적으로 불가능함. 따라서 기존 데이터 보존을 위해 **ext4** 파일 시스템을 그대로 유지함.
    
- **우분투 서버 OS 이슈**: 우분투 서버 버전 설치 시 기본적으로 LVM 구성은 원활하나 ZFS 네이티브 지원에 대한 추가적인 스터디가 필요해 귀찮음도 한몫함.
    

**② 데이터 소실 경험과 백업 부재 (Z640 시절)**

- **Immich 데이터 증발 사건**: Immich에서 라이브러리를 지우고 재등록하는 과정에서 파일이 휴지통으로 이동했고, 휴지통 비움이 실행되면서 원본 데이터가 날아가는 참사가 있었음.
    
- **백업의 한계**: 수 테라바이트에 달하는 방대한 용량 탓에 전체 백업 수단이 전무함. 하드를 추가로 구매하여 '원본 하드'와 '수정/작업 하드'를 물리적으로 분리하는 방안을 향후 과제로 남겨둠.
    

**③ 파티션 분리 계획 (`/mnt/work`)**

- 13600K 노드에서 귀찮음 때문에 LVM을 통으로 잡아 `/mnt/work` 하나로 쓰고 있으나, 루트 파티션 보호를 위해 향후 트랜스코딩 캐시, Docker 볼륨, 로컬 설정 파일용 파티션을 논리적으로 분할해야 함을 인지하고 있음.

### 3. 백업, 동기화 및 관리 전략의 디테일

**① 3중 복제 및 동기화 (Syncthing)**

- **대상**: 대용량 미디어 파일은 H4-Plus가 전담(Z640의 역할 계승)하고 복제하지 않음. 오직 컨테이너 DB, YML, 스크립트 등 **작고 중요한 설정 파일**들만 동기화 대상임.
    
- **방식**: H4-Plus, 13600K, 8505 Ubuntu VM 간에 Syncthing을 이용해 3중 복제 수행. 어디서 수정하든 즉각적으로 반영되는 델타(변경 블록) 동기화 방식을 채택함.
    

**② 인프라 형상 관리 (Git & Portainer)**

- **GitOps**: Docker Compose와 YML 파일은 중앙 Git에 올려 스냅샷처럼 버전 관리를 수행함.
    
- **관리 일원화**: Portainer + Agent 조합으로 분산된 노드들을 한 화면에서 관리. (참고: 복잡한 K8s나 Docker Swarm은 현재 인프라 규모에서 오버엔지니어링이라 판단하여 보류함).
    

**③ DB 및 시스템 백업 (스터디 필요)**

- **Postgres DB**: `pg_dump`를 통한 논리적 백업과, 필요시 Basebackup/WAL을 이용한 시점 복구(PITR)를 구상 중이나 아직 실제 구현은 안 됨.
    
- **i7 (13600K) 노드 백업**: LVM 스냅샷 마운트 후 **restic**으로 증분 백업(중복 제거 및 암호화 적용)을 구상 중이나, 백업 툴에 대한 지식이 부족해 추가 스터디가 필요함.

### 4. 네트워크 트래픽 제어 및 기타 디바이스

**① 인그레스(Ingress) 주도권 이전 계획**

- **현재**: 8505 노드의 Ubuntu VM에 설치된 Nginx가 역방향 프록시 및 내/외부 게이트웨이 역할을 수행 중.
    
- **미래**: 네트워크 라우팅과 프록시 역할을 일원화하기 위해, 향후 Nginx의 역할을 **pfSense(HAProxy 등)**로 완전히 넘기는 것을 계획 중임.
    

**② mDNS 및 WebDAV 활용**

- **mDNS**: 내부망 세그먼트 간 서비스 검색(Chromecast 등)을 원활하게 하기 위해 pfSense에 Avahi/mDNS 리플렉터를 세팅함.
    
- **WebDAV**: WireGuard VPN을 통한 외부 접속 시, 파일 탐색기 등에서 원활한 연결과 파일 스트리밍을 보장하기 위해 도입함.
    

**③ 클라이언트 기기 (FIREBAT A8 8845HS & MacBook)**

- **Firebat A8 (Windows)**: 서버랙 근처에 모니터/키보드를 물려둔 관리 및 프린트용 서브 PC. 평소에는 거의 안 쓰고 필요할 때만 RustDesk로 원격 접속해서 사용함.
    
- **메인 작업 환경**: 실제 주력 작업은 내 방에서 허브를 통해 모니터와 연결된 **MacBook**에서 이루어짐. 망 분리나 외부 접속은 WireGuard로 충분하여 클라이언트 PC의 활용도는 낮음.
